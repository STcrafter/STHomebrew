# Design: сохранение настроек списков

- Дата: 2026-11-27
- Статус: ждёт утверждения

## Зачем

При переходе в карточку и обратно, при обновлении страницы и при переключении разделов сейчас теряются поиск, фильтры, сортировка и переключатель «Только избранное». Пользователю приходится заново настраивать каждый список.

## Цели

1. Для каждого раздела (`monsters`, `spells`, `classes`, `subclasses`, `races`, `backgrounds`, `items`, `feats`, `homerules`) сохранить:
   - строку поиска;
   - выбранные фильтры в формате `{ include: [], exclude: [] }`;
   - поле сортировки и направление;
   - состояние «Только избранное».
2. Восстанавливать эти настройки при обновлении страницы, возврате из карточки (ссылкой или кнопкой «Назад») и переключении разделов.
3. Не добавлять зависимостей.

## Не-цели

- Не делать настройки передаваемыми по ссылке — пользователь выбрал сохранение в браузере.
- Не добавлять URL-параметры и не менять адреса карточек.
- Не сохранять раскрытие/сворачивание секций фильтров, позицию прокрутки и другие временные состояния интерфейса.
- Не добавлять кнопку «Сбросить настройки» (её можно будет сделать отдельной задачей).

## Подход

Выбранный пользователем подход: **`localStorage`, настройки хранятся отдельно по разделам**.

Реализация:

- Новый модуль `src/utils/listViewPreferences.js`:
  - `defaultListViewState` — `{ search: '', filters: {}, sortField: 'name', sortDirection: 'asc', showFavorites: false }`;
  - `loadListViewPreferences()` — читает ключ `listViewPreferences`, безопасно разбирает JSON и возвращает объект `{ [category]: state }`; при битых данных возвращает `{}`;
  - `saveListViewPreferences(preferences)` — пишет тот же объект в `localStorage` в одном ключе; это упрощает атомарное обновление всех разделов и избегает гонок при переключении категории. **Это моё уточнение варианта «один ключ на раздел»:** данные по-прежнему разделены по категориям внутри одного ключа, но запись идёт одной операцией; для пользователя разницы нет.
  - `normalizeListViewState(value, category)` — оставляет только допустимые поля: `sortField` проверяется через `getSortOptions(category)`, `sortDirection` — `asc/desc`, `filters` — массивы строк `include/exclude`, остальные — строки/логические значения. Незнакомые и повреждённые значения заменяются значениями по умолчанию.
- `CategoryList.jsx` хранит один объект `preferences` в состоянии; текущий раздел берёт `preferences[category] ?? defaultListViewState`. Любое изменение обновляет только состояние текущего раздела и сохраняет весь объект через `useEffect`. Сейчас `useEffect` при смене `category` сбрасывает настройки — он удаляется.
- `SearchBar.jsx` получает управляемое значение `value` (с сохранением работы без него) — поиск перестаёт жить только во внутреннем `useState`.
- `FilterPanel.jsx` получает `selected` и читает из него состояние чекбоксов; прямое изменение `options[field].selected` удаляется. Раскрытие секций остаётся локальным.

Совместимость: если в `localStorage` нет записи или она повреждена, список работает как сегодня. Тема и избранное используют `localStorage` по тому же шаблону, новый ключ их не задевает.

## Рассмотренные альтернативы

- **Параметры URL** — ссылка воспроизводима и «Назад» работает сам по себе, но вложенные фильтры нужно сериализовать, URL шумный, а ссылка «← К списку» требует отдельной доработки. Пользователь выбрал не это.
- **Только `sessionStorage`** — состояние терялось бы при закрытии вкладки и не делилось бы между вкладками браузера; слабее, чем `localStorage`.
- **`localStorage` + URL одновременно** — избыточная сложность для текущей задачи.

## Что остаётся на реализацию

- Чистые функции чтения/записи/нормализации с тестами `node:test` (включая битый JSON и неизвестные поля).
- Сделать `SearchBar` и `FilterPanel` управляемыми.
- Подключить сохранение в `CategoryList`, убрать сброс при смене раздела.
- Проверка: `npm test`, `npm run build`, в браузере — поиск/фильтры/сортировка выживают после обновления, перехода в карточку и обратно, переключения разделов; обычные страницы монстров не меняются.
